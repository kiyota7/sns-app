# AWSインフラ構成

sns-appをAWS上で動かすためのインフラ構成の概要。具体的なリソース定義や設定値は
`terraform/`ディレクトリのコードを正とするため、ここでは全体像とディレクトリ構成のみを示す。

タスクボード・家計簿アプリと同じ「EC2 + Terraform + SSM」構成を踏襲しているが、sns-appは
技術選定の時点で意図的にSQLite(ファイルベース)を選んでいるため、**RDSは使わない**。

## 全体構成図

```
[利用者のブラウザ]
        │ HTTP(80番)
        ▼
   ┌─────────────────────────────────────┐
   │              EC2インスタンス            │
   │  ┌───────────┐ ┌───────────┐          │
   │  │ frontend  │ │ backend   │          │
   │  │ (Nginx)   │→│(SpringBoot)│          │
   │  └───────────┘ └─────┬─────┘          │
   │                       │ /app/data      │
   │                       ▼                │
   │            ┌─────────────────────┐    │
   │            │ ./data (ホストボリューム) │    │
   │            │  - sns.db(SQLite)     │    │
   │            │  - uploads/(投稿画像)  │    │
   │            └─────────────────────┘    │
   └─────────────────────────────────────┘
```

- frontend・backendはEC2上でDocker Composeによりコンテナとして稼働する
- データベース(SQLite)と投稿画像は、EC2ホスト上の`/opt/app/data`ディレクトリを
  backendコンテナの`/app/data`にマウントして永続化する(RDS等のマネージドDBは使わない)。
  `git pull`で再デプロイしてもこのディレクトリは消えない
- EC2にはElastic IPを割り当て、アクセス先のIPが変わらないようにしている
- EC2の操作はSSH鍵を使わず、IAMロール経由のAWS Systems Manager(SSM) Session Managerで行う
  (SSH用ポートは開放していない)
- ネットワークはAWSアカウントに最初から用意されている「デフォルトVPC」を利用し、追加のVPC構築は行っていない

## リポジトリがPrivateであることによる差分

タスクボード・家計簿のGitHubリポジトリはPublicだが、sns-appはPrivateリポジトリのため、
EC2上の`git clone`には認証情報が必要になる。GitHubのFine-grained PAT(該当リポジトリのみ、
Contents: Read-only権限)を発行し、Terraformの`sensitive`変数として`terraform.tfvars`
(gitignore対象)に設定する。cloneのURLへの埋め込みはTerraform側で行い、EC2上のuser_dataスクリプト
自体にはPATを直接書かない(`terraform/ec2.tf`参照)。

同様に、JWT署名用の`JWT_SECRET`も本番用にランダム生成した値を`terraform.tfvars`で設定し、
EC2起動時に生成される`.env`経由でコンテナに渡す(リポジトリ内のデフォルト値は開発用)。

## IaC(Infrastructure as Code)によるコード管理

上記のインフラはすべて**Terraform**でコード化して管理しており、マネジメントコンソールの
手動操作は行わない。構築・変更は`terraform apply`、EC2内の操作は`aws ssm send-command`など、
AWS CLIベースの操作のみで完結する。

具体的なリソース定義(インスタンスサイズやストレージ量などの設定値を含む)は、
今後変更される可能性があるため本ドキュメントには記載せず、`terraform/`配下の各`.tf`ファイルを
直接参照すること。

## ディレクトリ構成

```
.
├── terraform/               # インフラのコード化(EC2・ネットワーク・IAM等。RDSはなし)
├── backend/Dockerfile       # backendコンテナのビルド定義
├── frontend/Dockerfile      # frontendコンテナのビルド定義
├── frontend/nginx.conf      # frontend内Nginxの配信設定・/api・/uploadsのリバースプロキシ設定
├── docker-compose.prod.yml  # 本番環境でfrontend・backendコンテナをまとめて起動する定義
├── .env.example              # 本番用環境変数のサンプル(実際の値は.gitignore対象)
└── scripts/deploy.sh         # コード変更時に、AWS CLI経由でEC2上のコンテナを再デプロイするスクリプト
```

## 運用の基本方針

- インフラそのものの新規構築・変更: `terraform apply`
- アプリのコード変更のみを反映する再デプロイ: `scripts/deploy.sh`
- 環境の削除(コスト停止): `terraform destroy`

いずれもAWSマネジメントコンソールやSSHを使わず、AWS CLIベースの操作で行う方針としている。

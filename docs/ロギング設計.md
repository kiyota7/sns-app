# ロギング設計

バックエンド(Spring Boot)の構造化ログの設計と、それを前提とした運用監視・障害対応の
考え方をまとめる。フロントエンドは対象外。

## 目的

これまでバックエンドにはログ出力の仕組みがなく、アプリケーションの動作は`mvn test`や
curlでの手動確認でしか把握できなかった。本番環境(EC2)で問題が起きた場合、
「いつ・誰が・何をしたときに・何が起きたか」を後から追跡する手段がない状態だった。

構造化ログ(1行1件のJSON形式)を導入することで、次を実現する。

- ログを人間が目で追うだけでなく、`jq`等での機械的な検索・集計ができる
- 1件のHTTPリクエストに関わる複数のログ行を、相関ID(`request_id`)で紐付けて追跡できる
- 将来的にログ集約基盤(CloudWatch Logs等)に転送する際、パース処理を書かずに
  そのまま取り込める

## ログの出力形式

標準出力(stdout)へ、1行1レコードのJSON形式で出力する(`backend/src/main/resources/logback-spring.xml`、
`net.logstash.logback:logstash-logback-encoder`使用)。EC2上ではDockerコンテナの標準出力として
`docker logs`から確認できる。

### 全ログ行に共通するフィールド

| フィールド | 内容 |
|---|---|
| `timestamp` | 出力時刻(ISO 8601) |
| `level` | ログレベル(`ERROR`/`WARN`/`INFO`) |
| `logger` | 出力元クラスの完全修飾名 |
| `message` | 人間が読むためのメッセージ本文 |
| `thread` | 出力したスレッド名 |
| `service` | 固定値`sns-app-backend`。将来的に他サービスのログと混ざっても区別できるように |

### リクエスト処理中のログ行に追加されるフィールド(MDC経由)

| フィールド | 内容 | 付与元 |
|---|---|---|
| `request_id` | リクエストごとの相関ID(UUID) | `RequestLoggingFilter` |
| `user_id` | 認証済みユーザーのID(未認証リクエストでは付与されない) | `JwtAuthenticationFilter` |

これらは[MDC](https://logback.qos.ch/manual/mdc.html)(Mapped Diagnostic Context)という
スレッドローカルな仕組みで管理しており、1つのリクエストを処理している間に出力される
すべてのログ行(コントローラー層・サービス層・例外ハンドラ等、どこで`log.info(...)`等を
呼んでも)に自動的に付与される。コード側で`request_id`を都度引き回す必要はない。

`RequestLoggingFilter`はレスポンスヘッダー`X-Request-Id`にも同じ値を返すため、
フロントエンドの開発者ツールやAPIクライアントからも、対応するログ行を検索する際の
手がかりとして使える。

## ログレベルの使い分け方針

| レベル | 使う場面 | 例 |
|---|---|---|
| `ERROR` | 想定外の例外。原因調査が必要 | `GlobalExceptionHandler`の`Exception`キャッチオール(NullPointerException、DB接続エラー等)。スタックトレース付きで記録する |
| `WARN` | 想定内だが注視すべき事象 | 業務例外(重複登録・投稿が見つからない等)、バリデーションエラー、リフレッシュトークンの再利用検知 |
| `INFO` | 通常運用で記録しておきたい事実 | アクセスログ(リクエスト完了) |
| `DEBUG` | 開発時の詳細調査用(現状未使用) | - |

「想定内のエラー(4xx)」と「想定外のエラー(5xx)」でレベルを分けているのがポイントで、
本番でERRORログの件数を監視するだけで「本当に調査すべき異常」を拾える設計にしている
(WARNは業務上普通に起こり得るので、ERRORほど即座の対応は不要なことが多い)。

## 実際のログ例

ログイン失敗(想定内の業務例外)とアクセスログが、同じ`request_id`で紐づく例:

```json
{"timestamp":"2026-08-04T19:52:10.123+09:00","level":"WARN","logger":"com.snsapp.exception.GlobalExceptionHandler","message":"business exception handled","request_id":"74e10075-7a30-4d2a-bf65-6da417e394ab","exception_type":"InvalidCredentialsException","status":401,"error_message":"メールアドレスまたはパスワードが正しくありません。","service":"sns-app-backend"}
{"timestamp":"2026-08-04T19:52:10.211+09:00","level":"INFO","logger":"com.snsapp.logging.RequestLoggingFilter","message":"request completed","request_id":"74e10075-7a30-4d2a-bf65-6da417e394ab","http_method":"POST","path":"/api/auth/login","status":401,"duration_ms":89,"service":"sns-app-backend"}
```

認証済みリクエストでは`user_id`も付与される:

```json
{"timestamp":"2026-08-04T19:53:02.884+09:00","level":"INFO","logger":"com.snsapp.logging.RequestLoggingFilter","message":"request completed","request_id":"cde5d480-0011-4e8d-a4e9-c0a12af7d8bc","user_id":"19","http_method":"GET","path":"/api/auth/me","status":200,"duration_ms":15,"service":"sns-app-backend"}
```

## 運用監視の観点

現時点ではログをEC2上のDocker標準出力に残しているだけで、CloudWatch Logs等への転送・
ダッシュボード化はまだ行っていない(「今後の拡張」参照)。ただし構造化しておくことで、
`docker logs`から取得したログに対して次のような監視・分析が`jq`等ですぐに行える設計にしている。

- **エラー率**: `level: ERROR`の件数を時間帯ごとに集計する。急増していれば障害の兆候
- **レイテンシ**: `message: "request completed"`の`duration_ms`を`path`ごとに集計し、
  遅くなっているエンドポイントを特定する
- **認証系の異常**: `exception_type: InvalidCredentialsException`のWARN件数の急増は、
  ブルートフォース攻撃やパスワードリスト攻撃の可能性がある
- **トークン盗難の兆候**: `message: "blacklisted refresh token reuse detected"`が
  出力された場合、そのユーザー(`username`フィールド)のリフレッシュトークンが
  何らかの形で漏洩し、正規利用者以外に使われた可能性がある。本来はリフレッシュトークンの
  ローテーション運用上、同じトークンが2回使われることはないため、これが出た時点で
  該当ユーザーへの追加確認や強制ログアウトの実施を検討すべきシグナルとなる

## 障害対応の観点(調査手順の例)

利用者から「投稿できない」等の申告があった場合の調査の流れ:

1. 発生時刻・利用者(可能であればユーザー名/メールアドレス)を確認する
2. EC2上で`docker logs sns-app-backend`を該当時刻付近で確認する
   (SSM Session Manager経由。SSHは使わない。詳細は[インフラ構成](インフラ構成.md)参照)
3. 該当利用者の`user_id`が分かれば、`jq 'select(.user_id=="<ID>")'`で絞り込む
4. `level: ERROR`または`level: WARN`のログ行を探し、`message`・`exception_type`・
   `error_message`から原因を特定する
5. `ERROR`ログには`stack_trace`フィールドが自動付与される(`logstash-logback-encoder`が
   例外オブジェクトから自動生成)ため、コードのどこで例外が発生したかを直接特定できる
6. 同じ`request_id`を持つ他のログ行(アクセスログ含む)を見れば、そのリクエストで
   何が起きたか一連の流れを追える

## 今後の拡張案(未実施)

- **ログ集約基盤への転送**: 現状ログはEC2上のDockerコンテナの標準出力に残るだけで、
  インスタンスを作り直すと過去ログは失われる。Dockerのログドライバを`awslogs`に変更するか、
  CloudWatch Agentを導入してCloudWatch Logsへ転送すれば、インスタンスのライフサイクルに
  依存せずログを保持・検索できるようになる
- **アラート**: CloudWatch Logsに転送した上で、メトリクスフィルタ(例:
  `level: ERROR`の件数)を設定し、閾値を超えたらSNS通知を飛ばすといった仕組みが考えられる
- **ローカル開発時の可読性**: 現状はローカル実行時も本番と同じJSON形式で出力される。
  開発体験を優先するなら、Spring Profileで分岐させ、ローカルのみ人間が読みやすい
  プレーンテキスト形式にすることも検討できる(今回はログ形式の一貫性を優先し、
  あえて分けていない)
